## Развилки — решить до начала работы

Обе переделывают половину задач, если решать их постфактум.

### A. Как код внутри `craft_execute_code` получает модули

`design.md` §6 (Tenet 4) фиксирует scope ровно из 7 имён:
`bot, Vec3, mcData, print, printJson, sleep, waitFor`. Рецептам нужны
`goals`, `Movements`, `Item` (prismarine-item). Конфликт не разрешён.

Варианты: расширить scope (правка спеки против её же принципа) либо
навесить нужное на бота в фабрике (`bot.pathfinder.goals` и т.п.),
оставив scope формально семичленным.

### B. Как по-настоящему прибить зависший скрипт

Сейчас никак (см. #1). Варианты: `worker_threads` (реально убиваемо,
но бот живёт в основном потоке — придётся гонять вызовы через мост)
либо оставить как есть и честно написать в README, что синхронный
цикл вешает сервер.

## Подтверждённые минусы

Ранжировано по последствиям.

### 1. Таймаут не прерывает скрипт; «sandbox» не изолирует
`plan:696` компилирует, `plan:713` вызывает.

`runInContext` возвращает функцию, `timeout` относится только к
мгновенной компиляции. `fn()` вызывается снаружи vm — там таймаута нет.
`Promise.race` реджектит, но выполнение не останавливает.

**Проверено запуском** (Node 26.3.0, точная форма из плана):

```
HUNG: still alive after 4s, killed   # while(true) при timeout: 300
```

Последствия: синхронный цикл вешает весь MCP-процесс намертво;
async-зависание «истекает» по таймауту, но продолжает менять мир в фоне.

Отдельно — изоляции нет вовсе, **проверено**:

```
process_escape   function   # this.constructor.constructor("return process")()
```

Для локального промо-тула риск приемлем, но слово «sandbox» это
оверселлит. Достаточно строки в README.

### 2. Рецепты физически не исполняются в этом контексте
`plan:1405` (navigation), `plan:1496` (building)

Свежий vm-контекст пуст. **Проверено запуском:**

```
require          undefined
setTimeout       undefined
console          object
dynamic import   THROWS: A dynamic import callback was not specified.
```

Флагманский фенс `building.md` начинается с
`new (require('prismarine-item')(bot.version))(...)` → `require is not defined`.
Рекомендуемая идиома навигации `await import('mineflayer-pathfinder')` →
тоже throws.

Отсутствие `setTimeout` бьёт по ходовым mineflayer-идиомам; `sleep`
закрывает не всё.

Зависит от развилки **A**.

### 3. Проверка рецептов слабее, чем обещает спека
`design.md:139` vs `plan:1463`

Спека дословно: «JS fences get a compile/lint contract test
(tsc/eslint over extracted fences)». План делает только
`new vm.Script(...)` — проверку парсинга.

Следствие: несуществующие переменные, запрещённый `require` и неверные
API проходят тесты зелёными. В связке с #2 это значит, что корпус
отгрузится сломанным при зелёном CI.

### 4. `world_name` нестабилен, хотя он routing key
`design.md:80` («stable slug»), `plan:421`

Слаг строится из MOTD, дедуп — суффиксами `-2`/`-3` по порядку обхода.
Порядок задаётся сбором UDP-датаграмм за окно 1.8 с, то есть
недетерминирован. `craft_list_worlds` и `craft_join_world` строят
снапшот независимо → ключ между вызовами может указать на другой мир.

Фикс: детерминированный суффикс от `host:port`.

### 5. Аудит и feedback не состыкованы
`plan:1197`, `plan:1274`

`craft_execute_code` объявляет `task_id`/`reason`, а деструктурирует
только `{ world_name, code, timeout }` — аудит-лог пуст.
`craft_execute_feedback` требует `execution_id`, который ни один tool
не возвращает. У steroid он идёт заголовком ответа execute_code.

### 6. Интеграционный тест обходит главный риск
`design.md:146`, `plan:1795`

Task 12 строит девятью `/setblock` — детерминированный путь. Реальный
promo-path (`bot.placeBlock`: reach ≤4.5, face-вектор, equip через
креатив-слот) отложен в ручной Task 13. Самое хрупкое место впервые
встретится на записи видео.

Дёшево закрывается установкой одного блока в креативе внутри Task 12.

### 7. Незаявленные зависимости
`plan:1348` (`import minecraftData from 'minecraft-data'`), `plan:52` (deps)

**Проверено:** `grep '"minecraft-data"|"prismarine-item"'` по плану →
не объявлены нигде. Оговорка: `minecraft-data` скорее всего
зарезолвится транзитивно через `mineflayer`, поэтому это мина, а не
немедленный отказ — сломается, когда mineflayer сменит свою версию.
`prismarine-item` moot: мёртв по #2.

### 8. Диапазон версий забит гвоздём
`plan:400` — `SUPPORTED_RANGE = ['1.18','1.21']`

На август 2026 это отвергнет актуальные миры как несовместимые.
Брать из `minecraft-data.supportedVersions.pc`.
(Локально проверить не смог: пакет не установлен, `MODULE_NOT_FOUND`.)

### 9. Порты для пинга не настраиваются пользователем
`design.md:76` («+ optional user-configured ports»), `plan:1134`, `plan:1619`

`extraPorts` существует только как внутренний параметр DI: CLI хардкодит
`[25565]`, сервер — `deps.extraPorts ?? [25565]`. Ни флага, ни env.
Требование спеки выброшено молча.

Рядом: пинги идут **последовательно** по 1.5 с на мир — просится
`Promise.all`. Само окно 1.8 с — осознанное следствие Tenet 3, не баг.

### 10. Типы в тестах не проверяются вообще
`plan:76` (tsconfig)

`rootDir: "src"`, `include: ["src"]` — папка `test/` вне компиляции,
а vitest транспилирует без type-check. TDD-цикл ни разу не зовёт
`tsc --noEmit`. Опечатка в тесте вылезет невнятной рантайм-ошибкой.

### 11. Требование спеки §8 про читы/gamemode потеряно
`design.md` §8

Спека просит сообщать в результате join, что мир без читов
(«legit survival mode only»). В плане этого нет ни в ответе
`craft_join_world`, ни в `craft_list_bots`. Данные доступны после
spawn через `bot.game.gameMode`.

### 12. `worldName` в JSON против `world_name` в параметрах
`design.md:93`, `plan:1041`

План декларирует это в self-review как намеренное. Различие бесплатно
вредное: модель будет путать поле ответа и имя параметра. Чинится
отдачей обоих ключей в JSON. Severity низкая — но и выгоды нет.

### 13. `LAN_PORT = 4445` захардкожен
`plan:530`

`test/sources.test.ts` и `test/cli.test.ts` оба его биндят, а vitest
гоняет файлы параллельно. Порт просится в параметр.

### 14. Скриншоты: success-path, скорее всего, мёртв
`plan:1330` + записка плана

План сам признаёт, что `headlessFrame` может не существовать в
установленной версии `prismarine-viewer`. Честнее сразу описать это как
«отгружаем ветку ошибки, успех опционален». **Не проверено** — нужна
установленная версия.

### 15. Мелочи, на которых встанет исполнитель
- `plan:464` обещает «6 PASS», тестов в Task 4 — пять (4 + 1).
  (В первой редакции стояло `plan:471` — ошибка ревью, исправлено.)
- `plan:1405`: в требованиях к `navigation.md` оставлен черновик —
  «`require(...)` — **NO**. Use the loaded plugin idiom». Агент прочитает

- ~~Нет tool-а «выйти из мира»... менеджер оставит запись `ready`
  с мёртвым ботом.~~ **Снято, это была ошибка ревью** — `plan:908`
  подписан на `end` и переводит запись в `error`. Реальные пробелы

### 16. Название файла не соответствует содержимому
`design.md:176`, `plan:1877`

Спека: M1 = «CLI + discovery + join + execute_code + 4 рецепта».

## Возражения Codex к этому разбору

Ниже — ответ именно на выводы этого документа. Исходный текст оставлен
выше без правок, чтобы не смешивать два ревью.

### 1. Вывод про версии у Codex не был «перевёрнут»

Проверка из плана считает совместимой любую строку `1.21.x`, не сверяясь
с реально установленным Mineflayer. Поэтому возможны ошибки в обе
стороны:

- новый протокольный патч внутри `1.21.x` будет принят даже тогда, когда
  установленная версия Mineflayer его ещё не поддерживает;
- `1.22.x`, `26.x` или другая новая схема версий будет отвергнута даже
  тогда, когда установленный стек её уже поддерживает.

Утверждение ревью, что поддерживать всю ветку `1.21` «как правило,
верно», не является контрактом совместимости. Патчи Minecraft меняют
протокол, а зависимости заданы диапазонами `^`, поэтому литерал
`['1.18', '1.21']` быстро расходится с фактически установленным стеком.

Предложение брать диапазон только из
`minecraft-data.supportedVersions.pc` тоже неполно: наличие данных о
версии не доказывает, что все используемые функции Mineflayer и
плагинов работают с ней. Источником истины должен быть тот же стек,
которым создаётся бот, либо реальная проба совместимости с понятным
результатом.

### 2. Нельзя считать небезопасный timeout приемлемым вариантом

С подтверждённой технической частью пунктов #1–#2 согласен полностью,
но не с выводом «для локального промо-тула риск приемлем, достаточно
строки в README». Код генерирует модель, а тривиальная ошибка
`while (true)` останавливает не только текущий вызов, но весь MCP-сервер.
Async-код после возвращённой ошибки продолжает менять мир. Это прежде
всего риск надёжности основного сценария, а не только security posture.

Ветка «оставить как есть и документировать» поэтому не годится для M1.
Нужна убиваемая граница выполнения. При этом `worker_threads` — не
drop-in fix: живой объект Mineflayer нельзя передать worker-у через
structured clone. Придётся либо держать внутри worker/process весь bot
runtime, либо строить RPC-мост к ограниченному API. Это архитектурное
решение, а не локальная правка Task 6.

### 3. Отсутствие `setTimeout` переоценено

`setTimeout` действительно отсутствует — это проверено. Но дизайн
намеренно предоставляет `sleep(ms)` и `waitFor(event, timeoutMs)`.
Рецепты продукта обязаны пользоваться публичным scope, а не случайными
Node-идиомами. Без конкретного сценария, который невозможно выразить
через эти две функции, отсутствие сырого `setTimeout` не является
отдельным дефектом.

Настоящий блокер здесь — `Item`, `goals` и `Movements`: без них
заявленные рецепты действительно не работают. Навешивание их на `bot`
сохраняет семь глобальных имён лишь формально, но добавляет собственный
wrapper layer и противоречит фразе спеки «native mineflayer idioms, no
wrapper layer». Честнее изменить публичный scope или заранее полностью
сконфигурировать pathfinder и дать явный поддерживаемый способ создавать
предметы.

### 4. `world_name` — не просто косметика низкой важности

Таблица `design.md` называет `world_name` routing key, а описание
`craft_list_worlds` говорит, что именно его инструмент возвращает.
Сервер же сериализует внутреннее поле `worldName`, после чего следующий
tool требует `world_name`. Для tool API, которым управляет модель, это
реальный разрыв producer/consumer-контракта, пусть и легко исправимый.

Отдавать оба поля, как предлагает ревью, не стоит: это создаёт два
источника истины. Лучше оставить camelCase внутри TypeScript, а на
границе MCP преобразовывать DTO в единый публичный snake_case.

### 5. M1/M2 — не только неверное имя файла

План действительно честно признаёт в self-review, что покрывает M1+M2.
Но это не превращает проблему только в нейминг. В текущем порядке нет
явного момента приёмки M1: M2-рецепты, скриншоты и README смешаны с
проверкой core-path, а недельная оценка M1 перестаёт соответствовать
исполняемому документу. Нужны либо два плана, либо явный milestone gate
после минимального набора задач.

### 6. Про UDP-тесты формулировка слишком сильная

Фиксированный порт ухудшает изоляцию тестов, но оба listener-а создаются
с `reuseAddr: true`. Поэтому параллельный bind не обязан упасть. Более
того, CLI-тест проверяет только валидность JSON и допускает непустой
результат, а тест listener-а использует `toContainEqual`. Случайно
полученная обоими сокетами датаграмма сама по себе эти assertions не
ломает.

Инъекция порта всё равно полезна, но называть это гарантированной гонкой
или блокером нельзя без воспроизведения на целевых ОС.

### 7. Про скриншоты сделан неподтверждённый прогноз

Из плана следует, что API не выбран и success-path не проверяется. Из
него не следует, что ветка «скорее всего мертва» или никогда не
заработает. Корректный минус: Task 8 содержит псевдокод с двумя
возможными API, но не содержит acceptance test для успешного кадра.
Нужно либо зафиксировать рабочий API установленной версии, либо явно
вынести success-path из M1.

### 8. «Мёртвая ready-запись» бота — ошибка этого ревью

Последний подпункт #15 неверен. `BotManager` подписывается на `error`,
`kicked` и `end`; при `end` запись переводится в `error`. Обычный
`bot.quit()` должен завершить соединение и вызвать `end`, поэтому
менеджер не оставит её в `ready`.

Реальные lifecycle-пробелы другие: нет join-timeout, старый бот явно не
завершается перед повторным join после произвольного `error`, а
`endAll()` нигде не подключён к shutdown MCP-сервера.

### 9. В самом ревью тоже есть неточные ссылки

Упрёк Codex за смещённые ссылки справедлив, но аналогичная ошибка есть
выше: «`plan:471` обещает 6 PASS». Строка 471 — конец команды commit;
ожидание `6 PASS` находится на `plan:464`. Это не меняет находку, но
подтверждает более общий вывод: line references обоих ревью нужно
проверять, особенно после редактирования документа.

### Итог разногласий

Основные блокеры Клод определил правильно: исполняемый scope рецептов,
неубиваемый код, нестабильная маршрутизация, разорванный feedback и
неадекватный smoke coverage. Ошибки находятся преимущественно в
severity: версионная ошибка двунаправленная, отсутствие `setTimeout` и

## Раунд 2: дыры, пропущенные обоими ревью

### 17. `printJson` — не ошибка компиляции, но молчаливо пустой ответ
`plan:690`

Заявленный диагноз неверен: `JSON.stringify` типизирован как
возвращающий `string`, а не `string | undefined`.
`lib.es5.d.ts:1169` — `stringify(value: any, replacer?, space?): string`.
**Проверено компиляцией** (tsc 5.6.3, `strict: true`):

```
tsc exit=0   # lines.push(JSON.stringify(value, null, 2)) — чисто
```

Но под неверным диагнозом лежит реальный дефект, и он хуже.
В рантайме `JSON.stringify(undefined)` возвращает `undefined` —
для `undefined`, функций и `Symbol`. Тип это **скрывает**, поэтому
strict TS его не поймает никогда. **Проверено запуском:**

```
lines = [null]                       # в массив легло undefined
lines.length = 1 -> HINT подавлен: true
join = ""                            # ответ tool-а — пустая строка
```

То есть `printJson(someUndefined)` даёт **пустой ответ без HINT и без
ошибки**: модель не может отличить «скрипт ничего не вернул» от
«скрипт не отработал». Для инструмента, где вывод — единственный канал
обратной связи, это тихий отказ в самом канале.

Фикс: в `printJson` отбивать `undefined` явно
(`const s = JSON.stringify(...); lines.push(s === undefined ? 'undefined' : s)`).

### 18. Screenshot отдаёт путь, а не изображение
`plan:1261` — `ok('screenshot written: ${path}')`

MCP умеет возвращать `{ type: 'image', data, mimeType }`, но tool
возвращает текст с путём к файлу в `tmpdir()`. Клиент не получит
картинку — ему придётся отдельно читать файл, а в не-локальном или
песочном клиенте это вообще не сработает. Мы при этом зеркалим
`steroid_take_screenshot`, который отдаёт image payload.

Смыкается с минусом #14: success-path не только с неизвестным API, но и
с неверным контрактом ответа.

### 19. Нет сериализации запусков на одном боте

Ни `BotManager`, ни сервер не сериализуют `craft_execute_code`. Два
параллельных вызова на один `world_name` будут одновременно двигать
бота и ставить блоки, ломая состояние друг друга: pathfinder получит
две цели, `placeBlock` — конкурирующие equip'ы.

MCP-клиент вправе слать параллельные tool calls, и модель это делает.
Фикс дешёвый: очередь (мьютекс) на `worldName`, лишний вызов либо ждёт,
либо получает внятную ошибку «busy».

### 20. Нет лимитов на код, вывод и timeout
`plan:1195` — `code: z.string()`, `timeout: z.number().optional()`

Ни `.max()` на код, ни границ на timeout, ни потолка на `lines[]`.
Последствия: `timeout: 999999` — «бесконечный» запуск, который вдобавок
нечем прервать (см. #1); цикл с `print()` копит массив до OOM; гигантский
вывод уезжает в ответ и сносит контекст модели.

Три числа в схему и обрезка вывода с пометкой «truncated» — правка на
полчаса, но сейчас все три ограничения отсутствуют.

### 21. «Полный bot API» плохо совместим с worker/RPC — ограничение для развилки B

Не дыра плана, а ограничение на его лечение, и важное. Если ботом
владеет worker, убийство worker-а по timeout **рвёт подключение к миру** —
то есть цена прерывания скрипта равна вылету бота. Если бот остаётся
снаружи, прозрачный RPC на произвольный API — отдельный большой проект,
несовместимый с недельным M1.

Значит у развилки **B** нет дешёвого решения, и выбирать придётся из
плохого: либо прерывание ценой реконнекта (приемлемо, если join быстрый
и состояние в мире, а не в боте), либо ограниченный API в worker вместо
обещанного «полного», либо отказ от прерывания с честной оговоркой.
Это надо решать явно, а не выводить из фразы «просто возьмём worker».

### 22. Ping теряет MOTD и число игроков
`design.md:76` vs `plan:398`

Спека: SLP «yields version, MOTD, player count». В плане
`PingSource = (host, port) => Promise<{ version: string } | null>` —
остальное выброшено. Следствие видно в выдаче: для `source: 'server'`
`displayName` собирается как `localhost:25565` вместо MOTD сервера,
хотя MOTD доступен из того же ответа. Число игроков не показывается
нигде, хотя спека его обещает.

### 23. ~~Слаг уничтожает любые нелатинские имена миров~~ — СНЯТО

**Решение владельца (2026-08-27): не чиним, кириллица не важна.**
Оставлено ниже как справка. Остаточный риск — недетерминированные
суффиксы — покрывается фиксом #4 (суффикс от `host:port`) независимо
от алфавита.
`plan:262`

`replace(/[^a-z0-9]+/g, '-')` вырезает всё, кроме ASCII. **Проверено
запуском** на реалистичных именах:

```
"Мой мир"           -> world
"Выживание 1.21"    -> 1-21
"マイクラ"             -> world-2
"Grigorii's world"  -> grigorii-s-world
```

Последствия жёстче, чем кажется. Routing key перестаёт быть
осмысленным (`1-21` для «Выживание 1.21»), а все кириллические имена
схлопываются в один base `world` — значит различать миры начинают
суффиксы `-2`/`-3`, и **минус #4 (недетерминированный порядок) из
редкого края становится нормой**. Для демо на машине
русскоязычного пользователя это основной сценарий, а не экзотика.

Ни один тест Task 3 не покрывает не-ASCII: там `Grigorii's world`,
`My -- World!!`, `!!!` и дедуп.

Фикс: транслитерация либо `normalize('NFKD')` + сохранение
unicode-букв (`\p{L}\p{N}` с флагом `u`), плюс детерминированный
суффикс от `host:port` (тот же фикс, что у #4).

### 24. Ошибки не содержат строку скрипта, обещанную спекой
`design.md:114` vs `plan:671`

Спека: «errors return message + stack + **the line of script**».
`ScriptError` несёт только `message` и `scriptStack`; строка исходника,
на которой упало, не извлекается нигде.

Хуже: скрипт оборачивается как `(async () => {\n${code}\n})`, то есть
номера строк в стеке **смещены на единицу** относительно того, что
писала модель, а `filename` — синтетический `craft-script.js`. Значит
даже имеющийся стек вводит в заблуждение, пока смещение не вычтено.

Для инструмента, где вывод — единственный канал обратной связи, это
прямо бьёт по итерации модели: она чинит не ту строку.
