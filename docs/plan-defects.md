# devrig-craft M1 — список недостатков плана

Дата: 2026-08-27 · источник: `docs/plan-review.md` · разбор:
`docs/plans/2026-08-27-devrig-craft-m1.md`

Нумерация сохранена из `plan-review.md`, поэтому идёт с пропусками.
**Снято владельцем:** #8 (жёсткий диапазон версий), #11 (читы/gamemode
в join-результате), #23 (кириллица в именах миров). Оставлены в конце

Статус проверки: **измерено** (запускал), **прочитано** (следует из

Для блокеров изменения не предлагаются — они архитектурные и оставлены

## Блокеры — решения за автором

### 1. Зависший скрипт не прерывается; изоляции нет
`plan:696` компилирует, `plan:713` вызывает · измерено

`timeout` у `runInContext` действует только на мгновенную компиляцию;
`fn()` вызывается вне vm. `Promise.race` реджектит, но выполнение не
останавливает. Синхронный `while(true)` вешает весь MCP-процесс
(проверено: жив через 4 с, убит снаружи). Async-зависание «истекает»,
но продолжает менять мир в фоне. Отдельно: `process` достижим из
скрипта через `this.constructor.constructor("return process")()`.

Ограничение на лечение: если бот уедет в worker, убийство worker-а рвёт
подключение к миру; если бот останется снаружи — прозрачный RPC на
произвольный API это отдельный проект. Дешёвого варианта нет.

### 2. Рецепты физически не исполняются в этом контексте
`plan:1405` (navigation), `plan:1496` (building) · измерено

В свежем vm-контексте нет `require`, нет `setTimeout`, динамический
`import` бросает `A dynamic import callback was not specified`.
Флагманский фенс `building.md` начинается с
`new (require('prismarine-item')(bot.version))(...)`, рекомендованная
идиома навигации — с `await import('mineflayer-pathfinder')`. Оба мертвы.
Спека при этом запрещает wrapper layer (`design.md:112`), а scope
фиксирован семью именами — конфликт не разрешён.

### 4. `world_name` нестабилен, хотя это routing key
`design.md:80` vs `plan:421` · прочитано

Дедуп суффиксами `-2`/`-3` идёт по порядку обхода, а порядок задаётся
сбором UDP-датаграмм за окно 1.8 с и недетерминирован.
`craft_list_worlds` и `craft_join_world` строят снапшот независимо,
поэтому ключ между двумя вызовами может указать на другой мир.

## Серьёзные

### 3. Проверка рецептов слабее, чем обещает спека
`design.md:139` vs `plan:1463` · прочитано

Спека требует «compile/lint contract test (tsc/eslint over extracted
fences)», план делает только `new vm.Script(...)` — парсинг.
Несуществующие переменные, запрещённый `require` и неверные API проходят
зелёными. В связке с #2 корпус отгрузится сломанным при зелёном CI.

**Возможное изменение.** Собирать каждый фенс во временный `.ts` с
заголовком-декларацией доступного scope (`declare const bot: Bot`,
`Vec3`, `mcData`, `print`, `printJson`, `sleep`, `waitFor`) и гонять
`tsc --noEmit` по получившейся папке. Тогда `require` в фенсе падает на
этапе теста, а не на демо. Тест становится настоящим исполнением
требования спеки, а не его ослабленной версией.

### 5. Аудит и feedback не состыкованы
`plan:1197`, `plan:1274` · прочитано

`craft_execute_code` объявляет `task_id`/`reason`, но деструктурирует
только `{ world_name, code, timeout }` — аудит-лог пуст.
`craft_execute_feedback` требует `execution_id`, которого ни один tool
не возвращает.

**Возможное изменение.** Генерировать `execution_id` (`randomUUID()`) в
`craft_execute_code` и отдавать его первой строкой ответа — как заголовок
у steroid. Туда же в stderr-лог писать `task_id`, `reason`,
`execution_id`, `world_name`, длительность. `craft_execute_feedback`
проверяет, что переданный id встречался, и иначе возвращает внятную
ошибку вместо молчаливого «recorded».

### 6. Smoke-тест обходит главный риск продукта
`design.md:146`, `plan:1795` · прочитано

Task 12 строит девятью `/setblock` — детерминированный путь. Реальный
promo-path (`bot.placeBlock`: reach ≤4.5, face-вектор, equip через
креатив-слот) отложен в ручной Task 13. Самое хрупкое место впервые
встретится на записи видео.

**Возможное изменение.** Добавить в Task 12 второй `it()`: креативный
equip одного блока, один `bot.placeBlock`, затем `blockAt`-проверка.
Отдельным тестом, чтобы падение физического пути было видно отдельно от
командного. Это ~15 строк и закрывает ровно тот API, который иначе
проверяется впервые на камеру.

### 17. `printJson` может вернуть пустой ответ без HINT и без ошибки
`plan:690` · измерено

`JSON.stringify` типизирован как возвращающий `string`, поэтому strict TS
это не поймает (проверено: `tsc 5.6.3 exit=0`). Но в рантайме для
`undefined`, функций и `Symbol` он возвращает `undefined`. Результат:
`lines = [undefined]`, `length > 0` → HINT подавлен, `join('\n')` → `""`.
Модель получает пустую строку и не может отличить «ничего не вернул» от
«не отработал».

**Возможное изменение.** В `printJson` отбивать случай явно:
`const s = JSON.stringify(v, null, 2); lines.push(s === undefined ? 'undefined' : s)`.
Плюс тест `printJson(undefined)` → строка `undefined`, а не пустой ответ.

### 18. Screenshot отдаёт путь к файлу, а не изображение
`plan:1261` · прочитано

Возвращается текст `screenshot written: /tmp/…`, хотя MCP умеет
`{ type: 'image', data, mimeType }`, а зеркалимый
`steroid_take_screenshot` отдаёт image payload. Клиент картинку не
получает.

**Возможное изменение.** Возвращать `content: [{ type: 'image', data:
<base64 PNG>, mimeType: 'image/png' }]`, а путь оставить вторым
текстовым блоком для человека. Смыкается с #14: пока API кадра не
зафиксирован, менять контракт ответа стоит одновременно с ним.

### 19. Нет сериализации запусков на одном боте
Task 7/8 · прочитано

Ни `BotManager`, ни сервер не сериализуют `craft_execute_code`. Два
параллельных вызова на один `world_name` одновременно двигают бота и
ставят блоки: pathfinder получает две цели, `placeBlock` —
конкурирующие equip'ы. MCP-клиент вправе слать параллельные вызовы.

**Возможное изменение.** Очередь на `worldName` в `BotManager`: поле
`private chain = Promise.resolve()`, каждый запуск встаёт в неё.
Выбор поведения при занятости — либо ждать, либо сразу вернуть
`err('bot busy: another script is running in this world')`. Второе
честнее для модели: она увидит причину, а не необъяснимую задержку.
Тот же замок закрывает `craft_chat`.

### 20. Нет лимитов на код, вывод и timeout
`plan:1195` · прочитано

Ни `.max()` на `code`, ни границ на `timeout`, ни потолка на `lines[]`.
`timeout: 999999` даёт «бесконечный» запуск, который вдобавок нечем
прервать (#1); цикл с `print()` копит массив до OOM; гигантский вывод
уезжает в ответ и сносит контекст модели.

**Возможное изменение.** Три границы в схему и одна в сандбокс:
`code: z.string().max(100_000)`, `timeout: z.number().int().min(1).max(600)`,
и потолок вывода в `executeScript` (напр. 256 КБ либо 2000 строк) с
обрезкой и явной последней строкой `[output truncated: N more lines]`.
Обрезать надо с конца, но сохранять хвост — там обычно результат
проверки.

### 24. В ошибках нет строки скрипта, а номера строк смещены
`design.md:114` vs `plan:671` · прочитано

Спека обещает «message + stack + **the line of script**». `ScriptError`
несёт только message и stack. Хуже: код оборачивается как
`(async () => {\n${code}\n})`, поэтому номера строк в стеке смещены на
единицу, а `filename` синтетический. Модель чинит не ту строку.

**Возможное изменение.** Передать `lineOffset: -1` в `runInContext`,
чтобы номера сошлись с тем, что писала модель (проверить на реальном
стеке — опция влияет на репортинг, а не на выполнение). И хранить
исходник рядом с `ScriptError`, чтобы к сообщению подклеивать саму
строку: `line 7: await bot.placeBlock(...)`.

## Потерянные требования спеки

### 9. Порты для пинга не настраиваются пользователем
`design.md:76` vs `plan:1134`, `plan:1619` · прочитано

Спека: «localhost:25565 (+ optional user-configured ports)». `extraPorts`
существует только как внутренний параметр DI: CLI хардкодит `[25565]`,
сервер — `deps.extraPorts ?? [25565]`. Ни флага, ни env. Рядом: пинги
идут последовательно по 1.5 с на мир.

**Возможное изменение.** Повторяемый флаг `--port` у CLI плюс
`DEVRIG_CRAFT_PORTS=25565,25566` как запасной путь (MCP-клиент часто
задаёт только команду, но окружение прокинуть умеет). Прокинуть в
`extraPorts`. Заодно заменить последовательный цикл пингов на
`Promise.all` — при трёх портах это 1.5 с вместо 4.5 с на каждый вызов
`craft_list_worlds`.

### 22. Ping теряет MOTD и число игроков
`design.md:76` vs `plan:398` · прочитано

Спека: SLP «yields version, MOTD, player count». `PingSource` возвращает
`{ version } | null`. Следствие видно в выдаче: для `source: 'server'`
`displayName` собирается как `localhost:25565` вместо MOTD сервера, хотя
MOTD лежит в том же ответе. Число игроков не показывается нигде.

**Возможное изменение.** Расширить `PingSource` до
`{ version, motd, players: { online, max } } | null`, брать MOTD как
`displayName` для `source: 'server'` (с фолбэком на `localhost:PORT`,
если MOTD пуст), добавить `players` в выдачу `craft_list_worlds`. Это
одновременно делает список полезнее: видно, что в мире уже кто-то есть.

### 28. Спека называет интеграционный тест «CI smoke test», но CI нигде нет
`design.md:161` vs план целиком · прочитано

Проверено грепом: в плане нет ни `.github/workflows`, ни любого другого
описания CI. Task 12 запускается только руками через
`npm run test:integration`. То есть заявленного «CI smoke test» не
существует — есть локальный тест, который никто не обязан запускать.

**Возможное изменение.** Добавить задачу с `.github/workflows/ci.yml`:
job `unit` на push/PR (`npm ci`, `tsc --noEmit`, `npm test`) и отдельный
job `integration` с Docker — по расписанию либо по ручному запуску, а не
на каждый PR, чтобы не платить пятью минутами за генерацию мира.

### 29. Юнит-тест на разбор ответов ping отсутствует
`design.md:157` vs `plan:514` · прочитано

Спека требует юнитов на «discovery parser (multicast payloads, **ping
responses**)». Тестируется только закрытый порт → `null`. Извлечение
`result.version.name` и поведение на неполном ответе не покрыты; план
явно откладывает это в интеграцию.

**Возможное изменение.** Замокать `minecraft-protocol` через
`vi.mock` и проверить три случая: нормальный ответ → `{ version }`,
ответ без `version.name` → `null`, брошенная ошибка → `null`. Это ловит
как раз тот класс поломок, который переживёт смену версии
`minecraft-protocol`.

### 30. Дистрибуция через `npx` обещана, но нигде не проверяется
`design.md:65`, `plan:1670` · прочитано

Весь quickstart стоит на `npx devrig-craft`, но проверка честности в
Task 11 запускает `node dist/cli.js --version` — то есть другой путь.
Правильность `bin`, `files` и того, что `resources/` доедут в пакет, не
проверяется ничем.

**Возможное изменение.** В шаг проверки Task 11 добавить
`npm pack && npx ./devrig-craft-0.1.0.tgz --version` и запрос рецепта
через собранный пакет. Это ловит и забытый `files` (#15.3), и
неправильный путь к `resources/`.

### 31. Мелкие расхождения со спекой
· прочитано

- `design.md:100` — feedback «logs locally», план пишет в stderr
  (`plan:1279`), то есть в лог клиента, а не локально.

**Возможное изменение.** Первое — писать JSONL в

## Гигиена и мелочи

### 7. Незаявленные зависимости
`plan:1348` vs `plan:52` · прочитано

`import minecraftData from 'minecraft-data'` есть, в `package.json`
пакета нет. Скорее всего зарезолвится транзитивно через `mineflayer` —
значит это мина (сломается, когда mineflayer сменит свою версию), а не
немедленный отказ.

**Возможное изменение.** Внести `minecraft-data` в `dependencies` в
Task 1, версией из того же диапазона, что тянет установленный
mineflayer (`npm ls minecraft-data` после установки).

### 10. Типы в тестах не проверяются вообще
`plan:76` · прочитано

`rootDir: "src"`, `include: ["src"]` — папка `test/` вне компиляции, а
vitest транспилирует без type-check. TDD-цикл ни разу не зовёт
`tsc --noEmit`.

**Возможное изменение.** Отдельный `tsconfig.test.json` c
`include: ["src","test","test-integration"]` и `noEmit`, а `npm test`
сделать `tsc -p tsconfig.test.json --noEmit && vitest run …`. Тогда
опечатка в тесте падает внятно и до запуска.

### 12. `worldName` в JSON против `world_name` в параметрах
`design.md:93` vs `plan:1041` · прочитано

Задекларировано в self-review как намеренное. Модель будет путать поле
ответа и имя параметра; выгоды от расхождения нет.

**Возможное изменение.** Один маппер на границе MCP: внутри TypeScript
остаётся camelCase, наружу уходит snake_case (`world_name`,
`display_name`, …). Плюс тест, что в JSON-выдаче нет ни одного
camelCase-ключа — иначе расхождение вернётся при первом же новом поле.

### 13. `LAN_PORT = 4445` захардкожен — ломает изоляцию тестов
`plan:530` · измерено

Два процесса биндят 4445 с `reuseAddr` без ошибки (проверено), но
unicast-датаграмма достаётся ровно одному сокету (проверено). Значит
listener из `cli.test.ts` может забрать тестовую датаграмму
`sources.test.ts` и уронить его `toContainEqual`. Независимо: второй
тест там — `toEqual([])`, точное сравнение с пустым массивом, которое
роняет любой реальный Minecraft-клиент в сети.

**Возможное изменение.** Вынести порт в параметр:
`collectLanAnnouncements(windowMs, port = 4445)`. Тесты берут свободный
порт, продакшн — дефолт. Второй тест переписать с `toEqual([])` на «не
содержит нашей метки»: он должен проверять фильтрацию, а не отсутствие
соседей в сети.

### 14. Screenshot: API не зафиксирован, acceptance-теста нет
`plan:1330` · не проверено

В Task 8 псевдокод с двумя возможными API `prismarine-viewer` и никакого
теста на успешный кадр.

**Возможное изменение.** Развилка по факту: поставить пакет, посмотреть
реальный API и зафиксировать его тестом на один кадр — либо признать
success-path вне M1 и оставить только ветку ошибки, но с тестом на неё.
Промежуточное состояние «псевдокод без проверки» — худшее из трёх.

### 15.1. Неверное ожидание в Task 4
`plan:464` — «Expected: 6 PASS», тестов там пять (4 + 1).

**Возможное изменение.** Поправить на 5.

### 15.2. Черновик редактирования в требованиях к рецепту
`plan:1405` — «`require(...)` — **NO**. Use the loaded plugin idiom».
Исполнитель прочитает это как содержание статьи.

**Возможное изменение.** Вычистить, оставив одну каноническую идиому —
ту, которая переживёт решение по развилке A.

### 15.3. `"files"` не попадает в `package.json` вовремя
`"files": ["dist","resources"]` упомянут запиской в Task 10, а
`package.json` пишется в Task 1.

**Возможное изменение.** Внести сразу в Task 1; проверку оставить на

### 16. Нет gate приёмки M1
`design.md:176` vs `plan:1877` · прочитано

Спека: M1 = «CLI + discovery + join + execute_code + 4 рецепта». План:
8 рецептов + скриншоты + README + ручной Prism-прогон, то есть M1+M2
(план сам это пишет). Момента «M1 готов» в документе нет.

**Возможное изменение.** Разрезать по спеке: Tasks 1–8, 10, 12 плюс
четыре рецепта (`skill`, `building`, `world-queries`,
`building-with-commands`) = M1 с явным критерием приёмки «`npm test`
зелёный и Task 12 проходит на чистой машине». Остальные четыре рецепта,
скриншоты, README и Task 13 — в отдельный файл M2. Заодно снимается
несоответствие имени файла содержимому.

## Lifecycle бота

### 25. Нет join-timeout
`plan:886` · прочитано

Если бот не спавнится и не падает, запись висит в `joining` бесконечно.
В Task 12 это маскируется циклом на 60 опросов.

**Возможное изменение.** Таймер в `join()` (60 с): если к его сроку
состояние всё ещё `joining` — перевести в `error` с текстом
`join timed out after 60s — is the world still open to LAN?`. Снимать
таймер по `spawn`.

### 26. Старый бот не завершается при повторном join
`plan:886` · прочитано

После `error` `join()` создаёт новый бот, не вызвав `existing.bot.end()`
— утечка сокета и возможный второй игрок в мире.

**Возможное изменение.** Перед созданием нового бота — `try { existing.bot.end() } catch {}`
и снятие подписок со старого эмиттера, чтобы его поздний `end` не
перевёл в `error` уже новую запись. Второе важнее первого: без него
свежий бот получит чужую ошибку.

### 27. `endAll()` не подключён к shutdown
